# Bounded Event order measurements

These measurements cover authenticated synchronous `POST /api/v1/orders` on the recorded local version, hardware, fixtures and 5–6 second workloads. They do not establish maximum throughput, a production SLA, or long term stability. The Event order path creates orders in a MySQL transaction.

## Setup and results

On 2026-09-25 the local application used Java 21.0.7, Spring Boot 3.5.16, MySQL 8.4, Redis 7.4, RabbitMQ 4.1, Docker Desktop 29.7.2 and k6 2.2.0. Each scenario used a new event, session and three tiers with capacity 300 each and up to 1,000 isolated sessions. Normal and Stress were fixed arrival rates for 5 seconds; Spike ramped up, held and down over 6 seconds. A single hot tier and round robin across three tiers are separate workloads. The [k6 driver](../../loadtest/event-orders-k6.js), [fixture](../../loadtest/seed-event-orders.sql), [inventory audit](../../loadtest/audit-event-orders.sql), and [SQL observation query](../../loadtest/observe-event-orders.sql) reproduce the measurement shape with isolated data. JSON summaries and SQL inventory audits are in [results](results/).

|---|---:|---:|---:|---:|---:|---:|
| Hot Normal | 20/s | 100 | 100 | 0 | 0 / 0 | 16.17 ms |
| Hot Stress | 80/s | 400 | 300 | 100 sold out | 0 / 0 | 16.07 ms |
| Hot Spike | 20→160→20/s | 679 | 300 | 379 sold out | 0 / 0 | 10.37 ms |

Every run's SQL audit found order count equal to reservation count, nonnegative inventory, `available + reserved + allocated = capacity`, and no duplicate buyer within a tier. `http_req_failed` includes expected 409 sold out responses, so the technical failure column comes from the script's dedicated counter. Offered arrival rate is not the observed successful write rate. These samples do not include payment or notification latency. Exact P50/P95/P99 and other counters remain in the JSON summaries, for example [hot Normal](results/event-hot-normal-20260925.json) and [multi tier Spike](results/event-multi-spike-20260925.json).

A separate [200 request order baseline](results/event-order-creation-baseline-20260919.md) used 32 bounded workers against capacity 100: 100 accepted, 100 business conflicts, zero technical failures or dropped attempts, P50/P95/P99 13.00/40.84/48.52 ms. It is a different version and load model.

## SQL and contention

The [SQL observation](results/event-sql-observe-20260925.txt) sampled about 2,426 orders. Idempotency lookup `EXPLAIN ANALYZE` was about 1.75 ms. The expiry scan used `ix_event_order_status_deadline` and took about 0.014 ms while no rows were due. Tier lock lookup used its primary key. An empty expiry result cannot predict a populated scan.

At 150/s for five seconds, hot tier and multi tier diagnostic runs each persisted about 750 orders. Instance wide InnoDB row lock waits increased by 153/601 ms and 224/969 ms respectively, with no deadlocks. A separate hot transaction window reached P95 426.37 ms and 57,228 ms cumulative instance wide lock wait; same rate hot windows before and after were roughly 17–20 ms P95 with much lower waits. The anomalous window coincided with initial request servlet initialization. These observations do not isolate one SQL statement or prove the tier row is a stable bottleneck. See [hot lock](results/event-hot-lock-after-20260925.txt), [multi tier lock](results/event-multi-lock-after-20260925.txt), and [transaction fixture audit](results/event-txn-fixtures-final-20260925.txt).

Hikari active/pending, JVM, HTTP status, Outbox backlog and oldest pending age were readable in the [metrics sample](results/event-metrics-20260925.txt); it is a point sample, not a wait time distribution or independent CPU trace. No admission protection or Event inventory bucketing was enabled from these short runs. Multi tier results must not be used as a single hot tier result.

## Short stepped load exploration (2026-09-25)

After the bounded measurements above, a separate local run explored where this setup begins to reject orders. The baseline source revision was `33a01b2` with the current V10 migration; the application was started by IntelliJ IDEA 2026.1.3 with Java 21.0.7 and the `local` profile. Windows k6 2.2.0 called `127.0.0.1:8081` while Compose MySQL 8.4, Redis 7.4 and RabbitMQ 4.1 were running. Each five-second constant-arrival-rate round used a new event and three new ticket tiers of 5,000 seats each, with up to 5,000 short-lived, isolated Redis sessions. A single-hot-tier round targeted only the first tier; the multi-tier round distributed requests across all three. There were no payments in this workload. Existing data and volumes were not cleared.

| Workload | Offered rate | HTTP requests | Accepted | Business rejected | Technical failures | Dropped iterations | P95 | P99 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Hot | 100/s | 501 | 501 | 0 | 0 | 0 | 277 ms | not captured |
| Hot | 200/s | 1,000 | 1,000 | 0 | 0 | 0 | 1,099 ms | not captured |
| Hot repeat | 200/s | 1,000 | 1,000 | 0 | 0 | 0 | 865 ms | 1,148 ms |
| Hot | 250/s | 1,251 | 1,218 | 0 | 33 | 0 | 3,011 ms | 3,205 ms |
| Hot | 300/s | 1,376 | 1,316 | 0 | 60 | 125 | 3,511 ms | not captured |
| Three tiers | 250/s | 1,251 | 1,233 | 0 | 18 | 0 | 2,903 ms | 3,265 ms |

The 300/s schedule called for about 1,500 iterations; 125 were dropped when k6 exhausted its 512 allocated VUs. They are neither HTTP responses nor accepted orders. Other rounds had no dropped iterations. The application log contains [Hikari connection acquisition timeouts](results/capacity-hikari-timeouts-20260925.txt) with all 32 connections active and requests waiting; this explains the observed server-side technical errors more directly than a speculative tier-row diagnosis. The three-tier run also failed at 250/s, so spreading these writes across three tiers did not remove the bottleneck in this setup. We did not record a same-window CPU trace or per-statement lock timing and cannot assign all latency to one database operation.

Two 200/s hot rounds completed without technical failures or drops; 250/s produced failures. **This brackets the observed five-second, no-failure offered rate between the tested 200/s and 250/s settings under these conditions.** It is not a measured maximum throughput, a sustained capacity bound, or an acceptable-latency target: P95 was already 865–1,099 ms at 200/s. On the 300/s round, successful completions averaged about 162/s over the whole run including response drain; that is not the offered rate or an independently measured steady-state service capacity.

[JSON summaries and matching SQL audits](results/) preserve all six rounds. At the end of each round, accepted HTTP orders equaled persisted orders and reservations; all three tiers had nonnegative inventory, unique buyers per tier and `available + reserved + allocated = capacity`. The hot 200/s repeat ended with 1,000 pending orders and 1,000 reservations on its 5,000-seat tier. Audit timing was before the normal payment deadline and expiry scan; eventual closure is outside this measurement. The archived Voucher table counts stayed unchanged. The short windows, existing host background activity, different preallocated VU counts, local simulated dependencies and missing CPU/lock attribution limit any generalization to another machine or production traffic.

## Synchronous-order capacity and overload measurements (2026-09-25)

The [consolidated A/B evidence](results/event-performance-ab-20260925.json) records 27 valid five-second runs: k6 P50/P95/P99 and outcome counters, sampled Hikari gauges, MySQL transaction and row-lock counter deltas, available Docker CPU samples, and the final per-tier inventory audit. Every run used the same Windows k6 2.2.0, IDEA Java 21 single application instance, Docker MySQL 8.4/Redis 7.4/RabbitMQ 4.1, 512 k6 VUs, a new 5,000-seat fixture per tier, distinct authenticated users and keys, and no payment. Expiry, payment recovery, and notification publishing were disabled in **all** A/B stages to isolate synchronous creation; existing data and volumes were preserved. An expired-token tuning attempt produced only authentication failures and is excluded. The earlier six-run exploration above used different background settings; the A/B comparison uses the measurements in this section.

### Bottleneck and change

The old creation path used seven SQL round trips per successful order, including a `JOIN ... FOR UPDATE` over tier, session, and event, a separate database clock read, and an in-transaction order reread. At 250/s for one hot tier, Hikari reached 32 active / 0 idle / 268 pending and its connection timeout count rose by 42; MySQL recorded 1,208 row-lock waits and 215,327 cumulative wait milliseconds. Three tiers sharing one session/event still had 42 technical failures, 268 pending, and 219,950 wait milliseconds. Container CPU was not sampled during these baseline windows, so this is not a CPU saturation claim. The MySQL transaction summary yielded approximately 92 ms mean across all transactions in the hot 250/s window and 94 ms in the three-tier window; those are instance-wide means, not per-order P95s. Statement digests showed the tier/session/event locking join dominated accumulated statement time; the inventory update, inserts, and reads were individually much shorter. Tomcat allowed 300 request threads against 32 Hikari connections, allowing lock-induced queues to grow until the three-second Hikari timeout.

The MySQL query now takes shared locks on event/session and an exclusive lock only on the tier (`FOR SHARE OF e,s FOR UPDATE OF t`); event publication/off-sale still serializes against an in-flight order. The H2 unit-test fallback retains its original `FOR UPDATE` because H2 does not parse MySQL's scoped locking clause. In-transaction order reread is removed: the insert and response use the same database-derived `created_at` value, so a successful HTTP response still follows committed MySQL order, reservation, and inventory writes. The successful path now uses six SQL round trips. Creation has a nonblocking, configurable 48-request admission limit; excess requests return HTTP 429 before the first SQL request and the permit is released after commit/rollback. Tomcat defaults to 128 max threads and accept count 256. Hikari stays at 32; there is no evidence that a larger pool addresses the row lock. RabbitMQ remains outside core order creation.

The scoped-lock-only A/B isolated the shared-row effect: three tiers at 250/s improved from 1,208 accepted / 42 technical failures / P95 3,128 ms / 268 Hikari pending / 219,950 row-lock wait ms to 1,251 accepted / zero technical failures / P95 287 ms / zero pending / 8,761 row-lock wait ms. Hot 250/s remained constrained (1,205 accepted, 45 technical failures, 268 pending), identifying the single tier row as the remaining hot-path lock. With admission and the removed reread, three tiers at 250/s completed 1,251/1,251, P50/P95/P99 9.27/14.79/23.43 ms, no rejection, timeout, or dropped iteration, zero pending, and only 147 cumulative row-lock wait ms.

### Final stepped results

All rates below are **offered** constant-arrival rates for five seconds; successes are committed business writes. Technical failures exclude controlled 429 responses. P50/P95/P99 describe HTTP requests including controlled responses, not successful writes alone. Each scenario's exact counts and per-tier SQL audit are in the evidence JSON.

- Hot 150/s: 751/751 and repeat 750/750 successful; zero 429, technical failures, and drops. P95 was 318 ms in the first warm-up affected round and 15 ms on repeat. Hot 180/s: 900/900 successful; zero 429/failures/drops; P50/P95/P99 9.75/27.51/29.08 ms; sampled Hikari active max 4 and pending max 0.
- Hot 200/s: one first-run sample had 945 writes and 55 controlled 429; warmed repeat had 977 writes and 23 controlled 429 out of 1,000. Both had zero technical failures and drops; repeat P50/P95/P99 190.84/303.48/363.75 ms; Hikari active max 32 and pending max 16. The old warmed 200/s baseline was 1,000/1,000 with zero technical failures, but P95 1,271 ms and pending max 121. The new 200/s setting is therefore an overload transition under this bounded policy, not a stable no-rejection tier.
- Hot 250/s: old 1,209 writes / 42 technical failures / no drops, P50/P95/P99 1,119/3,009/3,216 ms; final 898 writes / 353 controlled 429 / zero technical failures and drops, P50/P95/P99 228/371/443 ms. Hikari pending max fell from 268 to 16. Hot 300/s: old 1,276 writes / 58 technical failures / 167 dropped iterations, P95 3,538 ms; final 955 writes / 546 controlled 429 / zero technical failures or drops, P95 357 ms. Hot 400/s: final 999 writes / 1,002 controlled 429 / zero technical failures or drops, P95 327 ms. A scoped-lock-only 400/s intermediate still had 24 technical failures and 624 dropped iterations.
- Three tiers: old 250/s 1,208 writes / 42 technical failures / P95 3,128 ms; final 250/s 1,251/1,251 writes / P95 14.79 ms; final 300/s 1,501/1,501 / P95 38.91 ms; final 400/s 2,000/2,000 / P95 20.99 ms; final 500/s 2,501/2,501 / P95 21.39 ms. All final multi-tier runs had zero controlled rejection, technical failure, drop, and sampled Hikari pending. Five-second success at 500/s is a tested point, not a sustained limit or measured overload knee.

At the final hot 200/s repeat, MySQL recorded 962 row-lock waits and 115,804 cumulative wait milliseconds, compared with 977 writes; the final multi-tier 500/s sample had 485 waits and 2,905 wait milliseconds for 2,501 writes. Docker stats during the final warm runs sampled about 23–32% MySQL container CPU on the hot 150–200/s tiers and about 58% on multi-tier 500/s; these sparse readings exclude a CPU saturation finding. The transaction summary's mean includes the idempotency lookup's autocommit transaction and therefore is not a direct per-order transaction stopwatch. Lock wait deltas are also MySQL-instance-wide; isolated fixtures/background settings make them useful comparison signals, not exact attribution of every millisecond.

Every valid run's accepted count matched its final MySQL order and reservation counts; all audited tiers kept nonnegative inventory, unique buyers, and `available + reserved + allocated = capacity`. The final `mvn -Pinfrastructure verify` exited 0 with 65/65 unit tests and 83/83 infrastructure tests passing, including a real-MySQL check that the response creation time equals the persisted value. The infrastructure suite's existing 1,000-request fixture assumes no admission; its test-only permit is set to its 64 worker threads so it continues to verify exactly 100 successful and 900 sold-out outcomes. This test-only setting does not change the application default of 48.

### Optimization considerations

1. **Per-tier bounded admission** if hot tiers must preserve more successful writes or isolate one hot tier from other tiers. The present global limit does not harm the measured three-tier 500/s run, but per-tier permits may avoid unrelated requests sharing the same bulkhead. Implement only with explicit fairness, idempotency replay, and load A/B checks; do not make admission depend on Redis inventory.
2. **Shorten the remaining tier-lock transaction** if a measured SQL profile shows a specific round trip dominates. The separate database clock read occurs after acquiring the tier lock and preserves sale-window accuracy; folding it into the locking SELECT could read statement-start time before a long lock wait. Keep it until a replacement proves boundary semantics. Monitor `et_order` insert and reservation insert latency before changing them.
3. **Inventory stock buckets** are technically relevant only for a required single-hot-tier rate above the observed ~180/s no-rejection point: after scoped locks, one hot tier still accumulates roughly one row-lock wait per committed order, while 500/s distributed across tiers stays healthy. This is evidence of the hot tier row as a bottleneck, but does not by itself justify a schema and reconciliation change for this project. If a higher hot-tier target is set, first record warmed before/after at the same offered rates, committed writes, 429s, drops, lock waits, and inventory conservation. No bucket was added in this limited pass.
4. **Capacity and alerting**: keep Hikari active/idle/pending/timeout, controlled 429s, successful business writes, MySQL row-lock waits, and CPU visible together. Retest longer warm windows and background scanners enabled before claiming an operational SLO. Do not increase Hikari or Tomcat limits on the short local results alone.

## Isolated baseline and SQL observations (2026-09-24)

A separate disposable Docker fixture used one application instance, Hikari 32, and an open-loop Python driver before the current admission and transaction changes. Its single-tier runs completed 100/100 at 10/s for 10 seconds (p50/p95/p99 9.2/11.2/13.7 ms), 600/600 at 60/s for 10 seconds (7.6/9.9/14.2 ms), and 750/750 at 150/s for 5 seconds (5.7/8.0/14.1 ms), with zero technical failures or dropped iterations. The driver checked orders, reservations and conserved tier inventory. These short, different-environment samples are historical context, not the current A/B comparison.
