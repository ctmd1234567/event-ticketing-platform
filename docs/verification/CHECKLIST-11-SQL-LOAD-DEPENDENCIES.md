## Scope and setup

- Product path: authenticated `POST /api/v1/orders` to the synchronous `EventOrderService`, MySQL `et_*` tables. No Voucher endpoint, old k6 script, legacy Outbox, or asynchronous order creation participated. The item 7 baseline at `results/event-order-creation-baseline-20260919.md` recorded 100 orders and 100 sold-out conflicts from 200 requests at 32 bounded workers; it is a different workload and is not a throughput comparator.
- Host: Windows 11 / Docker Desktop 29.7.2, WSL2 Linux 6.18.33.2, Intel Core Ultra 9 275HX, 24 logical CPUs and 15 GiB WSL memory (measured during this run). Application image `eclipse-temurin:21-jre` (runtime log: Java 21.0.12); MySQL 8.4.11, Redis 7.4.11, RabbitMQ 4.1.8. Spring Boot 3.5.16, Java 21.0.7 for Maven tests. One application container, Hikari max 32, Tomcat max 300, default scan intervals. MySQL, Redis and RabbitMQ used separate `event-item11-*` containers and an isolated network, with no existing development volume attached. The app used ports 8083/8084 and the fixture containers used host ports 3308/6381/5674.
- Each load scenario created a fresh published Event and on-sale tiers, distinct Redis sessions and one idempotency key per request. No payment or order expiry occurred during these short runs. The Python standard-library driver schedules an open-loop request rate, bounds in-flight workers, records dropped scheduled iterations, and checks final `et_order`, reservation and tier inventory facts. It writes real orders and must be pointed only at disposable dependencies. Its run-specific IDs never delete other data. Command shape: `DOCKER_BIN=<docker executable> python3 loadtest/event-checklist11.py --scenario normal --rate 10 --duration 10 --workers 32 --tiers 1 --capacity 150 --output <result.json>`; the other scenario parameters are in the raw JSON files. A `Docker` CLI with access to named isolated MySQL/Redis containers and the isolated app is required.
- The first probe failed because the app's local profile bound to the container's own loopback; `SERVER_ADDRESS=0.0.0.0` fixed that before valid measurements. A later trial mapped large fixture user IDs through Lua's default scientific notation, merging user identities and producing 98 purchase-limit conflicts. The script now formats exact integer IDs. Those two invalid trials were discarded and are not included in the valid results below.

## SQL evidence and decision

`results/checklist11-sql-20260924.txt` stores the executed SQL and `EXPLAIN ANALYZE` output on MySQL 8.4.11 with 4,204 `et_order` rows and 25 tiers. A matching idempotency lookup returned one row in 0.0029 ms and uses `uk_event_order_idempotency` (confirmed by `SHOW INDEX`). The expiry scan used `ix_event_order_status_deadline` and returned zero due rows in 0.0956 ms. The tier/Event/Session lookup returned one row in about 0.0005 ms. These plans are small-dataset evidence; the empty due set limits the expiry conclusion. `EXPLAIN ANALYZE` was run on the reads, while the hot update was observed through the application load, InnoDB counters and a single isolated transaction: conditional tier update affected exactly one row and was rolled back. The production method also requires `changed == 1` before committing order and reservation.

The 150/s spike produced 16 global lock waits totaling 47 ms while all 750 writes completed with p99 14.1 ms and no dropped iteration or Hikari queue at the final scrape. This does not establish the tier row lock as the main bottleneck. There is likewise no observed overload rejection or technical failure that calls for Redis admission, Lua rate limiting, a fair semaphore or DB in-flight protection in this tested envelope. No such guard or stock buckets were added, so there is no before/after admission comparison to claim. The synchronous Event service remains the only core order path. A separate higher-load, longer-duration diagnosis would be needed before either change; the old Voucher 1500 RPS result is not an Event threshold.

## Dependency and restart evidence

- Redis stores login sessions and auth-code state. The token filter already fails closed on Redis `DataAccessException`; a live authenticated Event `GET /orders` returned 200 before Redis stop, 503 with `Authentication service is temporarily unavailable` after about 3.006 s during stop, and 200 after restart (first restored response about 0.724 s). No order operation is allowed by falling back to unverified identity.
- MySQL is the transaction source of truth. Before this task a database outage produced a generic 500. The focused connection/transaction failure handler now returns 503 `Database is temporarily unavailable`; an authenticated read returned 503 in 3.189 s and 200 after restart. A new Event order request returned 503 in 3.007 s during outage, then the same idempotency key returned 200 after recovery; persisted count for that key was exactly one. Other unexpected runtime errors continue through the existing 500 handler.
- RabbitMQ is used for Event notification, not order creation. With the isolated Broker stopped, `POST /orders/{id}/cancel` returned 200 in 19 ms and closed the order with its reservation released; inventory moved from 50/100/0 to 51/99/0. After Broker restart, the `ORDER_CLOSED` Outbox row reached `PUBLISHED` after two attempts and exactly one notification existed. The persisted Outbox-to-notification timestamp difference was four seconds; the columns have second resolution. This was one live event, not the item 9 fixed-100-event acceptance. The `event_outbox_backlog`, `event_outbox_oldest_pending_seconds`, and `event_outbox_manual_required` gauges expose the durable work state.
- With the isolated app stopped, one pending order's deadline was moved into the past in its disposable MySQL. On app restart the order became `CLOSED/PAYMENT_EXPIRED`, reservation became `RELEASED`, tier inventory changed to 201/599/0 out of 800, and its Outbox intent reached `PUBLISHED`. This directly exercises restart compensation for expiry; `EventOrderLifecycleIT` also tested four expired orders after a true context restart.
- `PaymentBoundaryIT.reconstructedStartupScannerRecoversPersistedUnknownPayment` covers a persisted payment `UNKNOWN` after scanner reconstruction, and `EventNotificationIT.publisherCrashBeforeAndAfterConfirmRecoversTheSameEvents` covers expired publisher claims and stable event IDs. These are deterministic integration tests, not live process-kill drills. The item 9 report retains its own larger Broker recovery boundary.
